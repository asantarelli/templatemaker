DrawPlus — Complete Programmer's Reference

The Clarion classes, their C rendering shims, and the GDI+ / Direct2D / direct-to-window engines behind CapeSoft Draw's antialiased backend. Everything below is drawn from the deployed source in C:\Clarion12\accessory\libsrc\win.

Antialiased 2D for Clarion 12 GDI+ · Direct2D · DirectWrite · WIC No redistributable

Overview top ↑

DrawPlus is an antialiased 2D drawing surface for Clarion — the smooth sibling of CapeSoft Draw. Every primitive (box, rounded rect, line, ellipse, arc, chord, pie, polygon, gradient, text) is rendered with vector antialiasing instead of Clarion's aliased software rasteriser.

It ships as a small stack: thin Clarion classes that expose a friendly drawing API, sitting on two hand-written C rendering shims that bind Windows' own graphics stacks — GDI+ for the default path and Direct2D + DirectWrite + WIC for the GPU path. There is no import library and no redistributable: both stacks ship with every modern Windows and are bound at runtime with LoadLibrary / GetProcAddress, so Clarion never links an MSVC COFF lib (which it cannot do).

Three things you can build with it:

Standalone canvas

Drive any IMAGE control with code-drawn antialiased graphics via DrawPlusClass and the DrawPlus control template.

Antialiased gauges

DrawPlusGaugeClass — colour bands, ticks, a value-ranged needle, hub and text, with five Draw-compatible design presets.

Draw, upgraded

DrawGdipClass subclasses CapeSoft DrawClass so existing Draw apps render antialiased when a global checkbox is ticked — no change to draw.clw.

Rendering pipelines top ↑

There are three distinct paths from a draw call to pixels on screen. Which one runs is decided by Backend and whether the canvas was opened with Start/Init (offscreen) or StartHwnd (direct-to-window).

1 · GDI+ offscreen → PNG default

Draw into an in-memory 32-bit ARGB GDI+ bitmap with SmoothingModeAntiAlias and antialiased text; on Display(), save a PNG into %TEMP% and point the IMAGE at it. The art survives repaints and prints for free, and the file alternates between two temp names (PngA/PngB) so the IMAGE always reloads a changed path.

draw calls ▶ GDI+ ARGB bitmap (AA) ▶ GdipSaveImageToFile (PNG in %TEMP%) ▶ IMAGE{PROP:Text} = path

2 · Direct2D offscreen → PNG Backend = 1

Rasterise with Direct2D into a WIC bitmap render target; d2_save ends the draw, encodes a PNG via the WIC PNG encoder, then re-begins so the canvas persists for the next frame. Same IMAGE/PNG delivery as GDI+ — a drop-in swap that rasterises ~15% faster but whose PNG encode is slower (see Performance).

draw calls ▶ D2D WIC render target (AA) ▶ WIC PNG encoder ▶ IMAGE{PROP:Text} = path

3 · Direct2D direct-to-window (GPU) Backend = 2

The fast path: bind the canvas to a window HWND with an ID2D1HwndRenderTarget and Present() flips straight to the screen — no PNG, no file I/O. Used for live/animated gauges. For a control (not the whole window) the shim spins up a small child host window over the control's pixel rect and renders into that. This is the "direct-to-memory / GPU" path detailed below.

draw calls ▶ ID2D1HwndRenderTarget ▶ Present() = EndDraw flips to screen (≈1280 fps raw)

Coordinates & colour conventions top ↑

  • Coordinates are pixels, origin top-left (0,0), x right, y down. Boxes are (x, y, width, height).
  • Colours are ordinary Clarion COLOR values — a colour equate, a 0x00BBGGRR literal, or a field. Pass -1 / COLOR:None for "no fill" / "transparent".
  • Angles (Arc/Chord/Pie/Radius) are degrees in math convention: 0 = 3 o'clock, increasing counter-clockwise — identical to CapeSoft Draw. DrawPlus converts to GDI+'s clockwise-from-3-o'clock internally.
  • Gauge angles (both gauge classes) are in tenths of a degree (0..3600), Draw's convention, so values and design presets transfer directly.
  • Colour on the wire: internally each Clarion COLOR is converted (with the global Alpha) to a 32-bit 0xAARRGGBB ARGB and passed to the C side by value — see ABI rules.

Choosing a backend top ↑

Set SELF.Backend before Start/Init. The template does this for you from the GloDraw checkboxes.

BackendValueWhen to use
GDI+ offscreen defaultdp:GdiPlus (0)Default. Best all-round for static/occasionally-updated art; PNG is free to print & persist. Full feature set (blur, grayscale, tiled/keyed images, overlay compositing).
Direct2D offscreendp:Direct2D (1)Same PNG delivery, GPU rasterisation. Marginally faster to draw; the WIC encode makes the round-trip slightly slower overall. A subset of features (see D2D notes).

On a D2D canvas these simply no-op rather than crash — they hit an empty GDI+ dispatch table. Keep those on the GDI+ backend.

DrawGdipClass Draw backend top ↑

A subclass of CapeSoft DrawClass that re-routes the common primitives through GDI+ (via a private DrawPlusClass canvas), leaving everything else to Draw's software rasteriser. Because all DrawClass methods are VIRTUAL, this needs no change to draw.clw.

Compositing model ("option b")

Each Display() blits Draw's software buffer as the base, then overlays the antialiased GDI+ layer on top (Cv.Overlay). Methods that aren't overridden here still draw (legacy look, composited underneath) — nothing breaks; overridden primitives just come out smooth on top. Z-order within a frame collapses to "all software under all GDI+". Windows only; reports keep the legacy path.

Overridden primitives (prototypes match DrawClass exactly): Init, Kill, Blank, Display, Resize, Box, RoundRect, Line, Ellipse, Arc, Chord, Polygon, Show, PutPixel, SetPenColor, SetPenWidth, SetFontColor, SetFont. Note Draw's coordinates are (1,1)-origin (the class subtracts 1) and Draw arc/chord angles are tenths (divided by 10 before calling in).

Turn it on app-wide with the Draw global template's "Use GDI+ rendering" checkbox, which makes Draw generate this class in place of DrawClass.

Why DrawNeedle is overridden On a value change the gauge calls DrawNeedle (via TakeEvent), not DrawGauge. The parent's software DrawNeedle + Display would blit the never-GDI+-rendered software buffer — a black gauge with just a needle. The override re-runs the full GDI+ DrawGauge and presents Cv.

GDI+ shim — dpcanvas.c top ↑

The default engine. Renders each primitive into a 32-bit ARGB GDI+ bitmap with SmoothingModeAntiAlias and antialiased text, then saves a PNG. It is a superset of myGaugePlus's gpcanvas.c and uses its own dp_* symbol names, so an app can use both accessories at once with no duplicate-symbol clash.

How it binds GDI+

  • No import lib, no redistributable. gdiplus.dll ships with every Windows since XP. The shim binds its flat C API at runtime with LoadLibrary + GetProcAddress (GdipCreateBitmap, GdipDrawArcI, GdipSaveImageToFile, …), so Clarion never links gdiplus.lib (it can't link MSVC COFF libs).
  • Compiled by Clacpp (Clarion's own C++ compiler) via PRAGMA('compile(dpcanvas.c)'). Exports are extern "C"; Clarion prototypes them in a MODULE('dpcanvas.c') block with NAME('_dpcanvas_xxx') (cdecl ⇒ leading underscore).
  • Hand-declared Win32 surface. Clacpp has no Windows SDK headers, so the shim declares the tiny slice it needs itself. It spells stdcall as pascal (#define WINAPI pascal) — Clacpp does not understand __stdcall.
  • Handle model. A canvas is a small int handle (1..DP_MAX); 0 = failure. All state lives C-side, keyed by handle.

Angle convention

Inside the shim angles are GDI+'s: degrees, 0 = 3 o'clock, sweeping clockwise (screen y grows down). DrawPlusClass takes the usual math angles (CCW) and converts before calling in — so callers never see the flip.

Direct2D shim — d2dcanvas.c top ↑

The GPU engine — Direct2D for shapes, DirectWrite for text, WIC for image decode/encode. Same antialiased results as GDI+, with an offscreen→PNG mode and a direct-to-window mode. Symbols are dpcanvas_d2d_*; Clarion prototypes them as d2_*.

The COM problem, and how it's solved

Direct2D is a COM API, not flat exports, and Clacpp has no DirectX headers. The shim therefore:

  • Binds exactly one flat entry point per DLL — D2D1CreateFactory, DWriteCreateFactory, and CoCreateInstance (for the WIC imaging factory).
  • Calls every method through hand-declared COM vtables. Only the slots actually called are typed; the rest are void* padding to hold the correct index. WINAPI is #defined to pascal (Clacpp's stdcall).
  • Verified that Clacpp compiles COM vtable calls, and that struct-by-value params (D2D1_POINT_2F to DrawLine) cross the boundary correctly.

Fast paths vs. the path builder

Rect, round-rect, ellipse, line, text and gradients have native D2D fast paths. Everything curved (arc, pie, chord, annular band, spline) is tessellated into points on the Clarion side (it has SIN/COS and the geometry) and streamed through a path builder — d2_path_begin → d2_path_point → d2_path_fill/d2_path_stroke. This keeps point arrays off the COM boundary (dodging the raw-array hazard) and keeps the C tiny. DrawPlusClass.D2Arc is the private helper that feeds the builder.

Offscreen lifecycle (Backend 1)

d2_begin(w,h) creates a WIC bitmap + render target and calls BeginDraw; d2_save does EndDraw + WIC PNG encode + re-BeginDraw (so the canvas persists for the next frame); d2_end releases.

Two hard-won D2D gotchas (1) Alpha mode. The WIC render-target pixel format's alpha mode must be PREMULTIPLIED (1) to match 32bppPBGRA. (2) DirectWrite text alignment differs from GDI+. DWrite is LEADING=0, TRAILING=1, CENTER=2 — so dp:AlignCenter(1) maps to 2 and dp:AlignRight(2) to 1, and the layout rect is pinned to (x,y) per alignment, or text lands ~4000px off-canvas. Also: IWICFormatConverter::Initialize is at vtable slot 8, not 3 (it derives from IWICBitmapSource, which inserts 5 methods first) — the wrong slot is an access violation.

Direct-to-memory / direct-to-window top ↑

Both offscreen backends draw into memory and then encode a PNG and hand the file to the IMAGE. Benchmarking showed the PNG encode + file I/O — not the rasteriser — dominates the frame. The direct-to-window path removes that round-trip entirely.

The bottleneck

Every offscreen primitive already renders into an in-memory ARGB buffer (a GDI+ ARGB bitmap, or a D2D WIC bitmap). The cost is delivery: GdipSaveImageToFile / the WIC encoder writes a PNG to %TEMP% and the IMAGE reloads it. At 400×300 with ~160 primitives, the encode + I/O is the majority of each frame (see Performance). That's fine for static art — the file gives you free printing and repaint-persistence — but it caps animation.

Killing the round-trip

The shipped answer is Direct2D direct-to-window via ID2D1HwndRenderTarget with presentOptions = RETAIN_CONTENTS | IMMEDIATELY. HwndRenderTarget derives from RenderTarget, so every draw function works unchanged — only the target and the "present" step differ:

Cv.StartHwnd(0{PROP:Handle}, w, h)   ! bind the canvas to a window HWND (GPU target)
! ...draw the frame with the normal primitives...
Cv.Present()                        ! EndDraw flips to screen — no PNG, no file

Rendering into a control (child host)

To target a single control rather than the whole window, the shim creates a bare WS_CHILD | WS_VISIBLE "STATIC" window (via CreateWindowExA, bound through GetProcAddress) positioned over the control's pixel rect, parented to the Clarion window HWND: dpcanvas_make_child / move_child / destroy_child. The DrawGdipGaugeClass Backend 2 path uses this — reading the control rect via PROP:Xpos/Ypos/Width/Height, creating a host, then StartHwnd on it; Resize repositions the host and rebuilds the target; Destruct destroys it. The gauge coexists with normal Clarion controls on the same window.

Also possible: GDI+ blit-to-HDC Because GDI+ already draws into our own in-memory ARGB scan0 buffer, a second file-free route is to StretchDIBits / AlphaBlend that buffer straight to the control HDC. The shim already declares the needed GDI surface (GetDC, CreateCompatibleDC, BitBlt, LockBits) for GrabScreen/Blur. Both file-free routes require the control template to repaint on EVENT:Drawn and give up the file's free print/persistence.

Performance findings top ↑

Measured at 400×300, ~160 primitives + text, CLOCK() centisecond timing, draw and save split by A–B method timing:

GDI+ offscreen → PNG4.232362.202.03

  • D2D rasterises ~15% faster than GDI+, but its WIC PNG encode is ~38% slower, so for the offscreen race GDI+ wins overall — the encode + file I/O dominates.
  • Direct-to-window is ~5–6× faster because it drops the PNG round-trip entirely. Live demos run timer-paced at ~60 fps; raw throughput is ~1280 fps.

Rule of thumb: static or occasional art → GDI+ offscreen (simplest, prints/persists free); live animation → Direct2D direct-to-window.

ABI & boundary rules top ↑

The Clarion↔C boundary is kept deliberately narrow and by-value to stay safe under Clacpp:

On the wireRule
Coordinates & anglesCross as C double (Clarion REAL), cast to float inside — avoids any 4-vs-8-byte float mismatch.
Colours32-bit 0xAARRGGBB ARGB, Clarion ULONG, by value.
Stringschar* (Clarion *CSTRING, RAW); converted to UTF-16 inside.
CanvasA small int handle (1..max); 0 = failure. All state lives C-side.
Calling conventioncdecl ⇒ C symbols carry a leading underscore; Clarion binds them with NAME('_dpcanvas_xxx'). Win32 imports use pascal (Clacpp's stdcall).
Point arraysKept off the boundary for D2D (tessellated Clarion-side). For GDI+ they pass as *REAL … RAW; only Polygon is fragile mid-frame (use FillTriangle).

Gotchas & constraints top ↑

Deployed source must be CRLF Heredoc-appended or Write-created .inc/.clw files are LF. Deployed Clarion source must be CRLF or the compiler reports a bogus "Illegal data type". Always convert the deployed copy in accessory\libsrc, not just the examples copy.
Include at %AfterGlobalIncludes, not %CustomGlobalDeclarations A control/extension template must INCLUDE its class .INC at the PROGRAM-module global scope (%AfterGlobalIncludes). In a multi-DLL / multi-module ABC app the procedure is generated into a MEMBER module; PROGRAM-module globals are visible there, but %CustomGlobalDeclarations is not — so the class TYPE is unknown in the member and you get "Illegal data type: <CLASS>" cascading into every method. (In Clarion an unknown label used as a type says "Illegal data type"; an unknown value says "Unknown identifier".)
  • Polygon mid-frame mis-reads its args unless it is the first draw call — use FillTriangle (all by-value). See the warning under Primitives.
  • Gauge bands must use FillBand (filled annular sector), not a thick stroked Arc — a fat stroke bulges outside the path and its caps leave wedge gaps.
  • Semi gauges: point maths (ticks/labels/needle/hub) rotate around the ellipse centre (gy + gh/2), not CapeSoft's bottom pivot cy — using cy lands them off the bottom of the canvas.
  • Template guards that emit a DrawGdip-only property (obj.Backend, self.ModernLook) must be guarded by the actual swapped class name (%BaseClass='DrawGdipGaugeClass' / 'DrawGdipClass'), not just the %gUseGdiPlus flag — non-circle gauge styles stay their legacy class and lack the field ("Field not found: BACKEND").
  • Array limits: one Clarion array maxes at 65535 bytes (LONG,DIM ≤ 16383); overrunning makes the whole CLASS "Illegal data type" at every use site. % is not modulo — use i - INT(i/3)*3 or BAND().
  • Reserved words: by is reserved (LOOP..BY) — it can't be a variable name.

Build & deployment top ↑

What compiles what

DrawPlusClass.clw pulls both C shims into the build:

  PRAGMA('compile(dpcanvas.c)')     ! GDI+ shim
  PRAGMA('compile(d2dcanvas.c)')    ! Direct2D shim (compiled unconditionally)
  MAP
    MODULE('d2dcanvas.c')  ! d2_* -> _dpcanvas_d2d_*
    MODULE('dpcanvas.c')   ! dp_* -> _dpcanvas_*
  END

Both PRAGMAs are unconditional, so both .c files must ship even for a GDI+-only build — omitting d2dcanvas.c fails the compile regardless of the Direct2D checkbox.
